# Crash-safe runner

The crash-safe runner is the mandatory host-safety boundary for
resource-intensive benchmark, experiment, fixture, and Lamina commands in the
practical-runtime program. It controls and measures the complete descendant
tree on supported Linux hosts.

<Callout type="warning">
  A safety-limit hit is a failed scenario. Never report it as a product
  measurement, rerun it without limits, add swap, or alter host/kernel memory
  behavior.
</Callout>

## 1. Inspect the effective envelope

```bash
npm run safe:envelope
```

This command is read-only. It reports host memory and disk, derived limits,
cgroup-v2 controller availability, the selected adapter, current self-test
attestation, and completed tier promotions. It does not create a scope or
launch a payload.

The default hard memory ceiling is `min(3 GiB, 25% of physical RAM)`. The 8 GB
profile cannot exceed 2 GiB, and launch must preserve at least 2 GiB for the
OS/desktop. The default process ceiling is 64 and production concurrency is
one.

## 2. Qualify the current host and runner build

```bash
npm run safe:self-test
```

The self-test uses only tiny fixtures and low artificial limits. It covers:

- direct and aggregate child memory;
- ignored graceful termination and timeout;
- rapid process spawning;
- stdout/stderr flooding;
- runner-owned temporary-file growth;
- parent interruption;
- stale PID identity; and
- a parent that exits with a detached descendant.

Every case writes a versioned report, proves cleanup, and contributes a digest
to the host attestation. The attestation is invalidated when the host,
architecture, controllers, adapter, runner source, gate, or schema changes.

If user-systemd or cgroup-v2 aggregate enforcement is unavailable, the
portable adapter can run only the exact built-in low-limit self-test allowlist.
The host-qualification command itself refuses before launching the adversarial
matrix, because a portable process group cannot prove cleanup of the detached
descendant case. Portable focused contract tests never qualify medium or large
execution.

The low-limit Linux CI job is pinned to Ubuntu 22.04 and provisions Bubblewrap
without privilege. It downloads the official Debian Bookworm 0.8.0 package by
an immutable URL, verifies the pinned SHA-256 digest, records package and ABI
dependency evidence, and extracts only the binary into the ephemeral runner
directory. Bookworm's declared glibc, libcap, and libselinux minima are
satisfied by Jammy. The job then runs the real hard-quota probe before the
adversarial matrix; it does not use `sudo` or modify the host package database.
Ubuntu 24.04's hosted AppArmor policy blocks this rootless namespace path
unless a privileged package profile is installed, so it is not used as the
qualification host.

Hosted CI preserves either a complete production attestation or the exact
nonzero production-enforcement refusal as an artifact. A portable refusal is
truthful CI evidence, never medium/large qualification.

The native release workflow runs source-quality checks on every target before
an adapter qualification gate. Until issue #57 supplies production enforcement
for macOS and Windows, those targets refuse qualification and the workflow does
not enter packaging or artifact-upload steps.

## 3. Run one scenario

```bash
npm run safe:run -- \
  --tier small \
  --workload retrieval-v1 \
  --report /absolute/path/to/small-result.json \
  --promote \
  -- <command> [args]
```

Use `--promote` only for an intended tier-qualification scenario. The stable
`--workload` identifier, redacted child-command digest, referenced file digest,
and bounded Git source snapshot bind smaller-tier evidence to the same workload;
success from a trivial, replaced, or different command cannot unlock another
workload.
The snapshot follows the Git roots of absolute audited entrypoints even when
the workload directory is outside Git. Changed files are content-hashed with a
bounded streaming reader; files above the promotion bound refuse qualification
instead of falling back to size and timestamp identity.
Promotion is
recorded only after a successful command, schema-valid report, empty descendant
set, removed scope, removed runner temporary directory, and error-free cleanup.

Medium requires current small promotion. Large requires current small and
medium promotion. Both also require a valid production attestation, aggregate
enforcement, and the global concurrency lock. Every tier refuses while an
existing Lamina runtime is already active, because a pre-existing process is
outside the new scope.

Before launch, a durable ledger writes one atomic entry per run under a bounded
command/build shard for the active repository, command, referenced workload files,
runner build, and fixed concurrency. It is
cleared only after a classified result with verified cleanup. A safety-limit
observation converts that entry to a durable fence, and a limit-only change does
not bypass it. The relevant command shard is checked directly rather than scanning
unrelated failures globally, and
independent run files prevent concurrent small runs from overwriting one another.
Incomplete cleanup, controller `SIGKILL`, a lost session, or later distinct
failures cannot erase or overwrite earlier fences. A command/build shard is
capped at 64 records, a repository at 256 shards, and the host ledger at 256
repositories. Capacity converts the affected scope to one durable saturation
fence that refuses later unsafe allocations; it never forgets an old failure
or silently permits the command. A verified successful run removes its last
active record and atomically reclaims the empty command shard and repository,
so healthy sequential work does not consume failure capacity. The same
process-identity locks sweep stale mutation candidates and release/stale
quarantines left by a killed controller.

All limit flags are downward-only:

```text
--memory-mib --memory-high-mib --pids --timeout-ms
--output-mib --temporary-mib --sample-ms --high-samples --grace-ms
```

There is no unrestricted fallback. Only exact reviewed internal entrypoints are
accepted; `npx` must name the reviewed tool in the first argument, and unknown
shell, package, generated, oversized, or indirect launchers
fail closed. Docker, Podman, Harbor, and the LB6 daemon entrypoints are refused
because the client scope cannot prove ownership of daemon-created descendants.
Adding an entrypoint requires a code change and review, not a caller flag.

On Linux the payload runs in an unprivileged bwrap mount namespace. The host
root is read-only, the declared working tree is the explicit writable workload
surface, and the runner temporary directory is a size-limited private tmpfs.
Nested read-only mounts cover the safe-runner implementation, the CLI package,
its dependency tree, and reviewed graphd fixtures even when the Lamina source
tree itself is the writable workload. Thus a scoped command cannot rewrite a
transitive graphd module and then ask the broker to bless it.
The controller verifies that tmpfs before releasing the payload and reads its
allocated blocks and inode usage through `/proc/<pid>/root`; this accounts for
deleted-but-open files without an unbounded directory scan. Symlinks in the
temporary tree, inode storms, quota exhaustion, or absence of this enforcement
capability fail closed.

Lamina's own `graphd` is a narrow managed-daemon exception, not a detached-tree
escape hatch. When a scoped CLI starts `graphd`, the client asks the live
supervisor broker to authorize its PID, Linux start identity, command, parent,
and canonical socket/lock paths. The graph root must resolve to a Git repository,
and the socket and lock must be exact children of its Git-common `lamina`
runtime directory. For source execution, the client opens the reviewed
`server.mjs` before spawn and Node executes that inherited descriptor. The
broker hashes `/proc/<pid>/fd/3` against a trusted digest captured before the
payload starts, so replacing the mutable pathname after code load cannot grant
managed status. It also verifies from the child mount table that the effective
CLI/dependency/fixture closure is read-only. Standalone execution must match the controller's already-open
executable digest. The broker captures the directory's
device/inode/owner identity and the graphd PID/start identity for crash cleanup.
The lock must carry that same process identity before either runtime entry can
be removed. Each starter holds a unique PID/start-tick/nonce claim for its
lifetime and proceeds only when no other live graphd or cleanup claim exists.
This serializes stale-lock replacement against other starters and watchdog
cleanup. On macOS and Windows, where a reusable PID cannot be paired with Linux
start ticks, a conservative fixed operation claim serializes startup and stale
lock replacement. A crash-stale portable claim fails closed instead of being
automatically replaced, and client shutdown refuses OS signals if authenticated
shutdown does not stop the PID-only target. No child-writable registry, mutable source
pathname, or PID-only signal target is authoritative. After the CLI
exits, the runner accepts only that exact registered `server.mjs`/`--graphd`
root and its in-scope descendants, sends the complete scope `SIGTERM`, and
still requires an empty scope. A mismatched identity, unrelated process, or
unregistered detached descendant is a safety failure.

Before payload launch, the controller starts a detached watchdog with a
random disarm token and an atomic manifest. The manifest holds exact PID start
identities, the transient systemd unit/cgroup, registered graphd paths, the
production lock identity, and device/inode identities for runner-created
temporary directories. Normal completion durably writes the report and then
disarms the watchdog. If the controller is killed or crashes first, the
watchdog validates each systemd operation, requires the exact unit to be
absent, removes only identity-matched runner state, and writes a schema-valid
`internal_error` report with termination reason `controller_crashed`.

## Reports and outcomes

Each run writes `lamina.safe-runner-report/v1`. It includes:

- limits and complete preflight data;
- aggregate process RSS and cgroup `memory.current`/`memory.peak` as distinct
  measures, plus bounded per-process samples and peaks;
- bounded output counts/tails and temporary disk usage;
- every observed descendant with PID start identity;
- cgroup memory/PID events;
- exit status, signal, termination reason, and requested signals; and
- descendant, scope, temporary-directory, lock, and report cleanup.

Host attestation binds the evidence to the boot ID, kernel release, systemd
version, user-manager identity, root controller/subtree state, architecture,
adapter, schemas, runner sources, graphd integration, and adversarial fixture.

The outcome is one of `success`, `command_failed`,
`safety_limit_exceeded`, `preflight_refused`, `interrupted`, or
`internal_error`. Validate a report independently with:

```bash
node scripts/safe-runner/cli.mjs validate-report --file /absolute/path/to/result.json
```

If the requested report path cannot be written, the runner attempts a bounded
fallback report in the system temporary directory and marks the run as an
internal failure. A missing report is never a measurement.

Reports deliberately omit the child environment and redact common credential
flags, bearer tokens, URL userinfo, and secret-like output patterns. Redaction
is defense in depth, not a data-loss-prevention guarantee: commands can print
arbitrary sensitive material. Treat reports as sensitive diagnostics, keep
them mode `0600`, review them before sharing, and never publish raw reports or
CI artifacts containing real credentials.

## Child-command integration

Resource-intensive repository entrypoints can call
`assertSafeRunnerContext()` from `scripts/safe-runner/index.mjs`. It obtains
the authoritative tier, unit, and limits from a live supervisor-held broker,
then independently reads the caller's cgroup and controller values. Context
files, tokens, tier variables, and plain environment flags are not proof.

Lamina's graph client also registers any graphd it starts by PID and Linux
start ticks. After the payload exits, the runner gives that exact registered
daemon a short graceful shutdown window and verifies that its socket, daemon
lock, operation claim,
process tree, and scope are gone. Any unregistered detached process—or any
registered graphd that outlives the deadline—fails the scenario and triggers
complete scope termination.

A stale claim is removed only when its PID/start identity is dead. A stale
daemon lock with a reused live PID is likewise treated as stale without
signalling that unrelated process. A new graphd may replace it only while
holding the sole live operation claim.

for the ownership and fail-closed rationale.
