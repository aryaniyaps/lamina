# Give your coding agent product memory it can trust

Lamina is a **transactional product graph** for AI coding agents. It turns product intent, source observations, personas, workflows, invariants, and verification evidence into versioned knowledge your agent can query without treating a pile of prose as canonical truth.

The developer journey is:

1. **Install** the CLI and agent skills.
2. **Initialize product knowledge** for the repository.
3. **Design one workflow** in a graph session and publish it atomically.
4. **Implement from the resolved `GraphVersion`** in ordinary coding mode.
5. **Verify the live product** through an independent Mission for every relevant Persona.

```bash
npm install -g @laminadev/cli@latest
npx skills add aryaniyaps/lamina --all -y
lamina doctor --json
```

Start a fresh agent session, then run:

```text
/lamina-init <product domain and primary users>
/lamina-design <one workflow>
```

Your coding agent implements the returned projection. Lamina never edits application source. When the product is running:

```text
/lamina-verify <workflow> at http://localhost:3000
```

## What is canonical?

- Ladybug at `$(git rev-parse --git-common-dir)/lamina/graph.lbdb` is the canonical graph for the clone.
- `graphd` is the only writer. Every worktree talks to the same authenticated daemon.
- CocoIndex contributes explicit source `Observation` records; it never opens Ladybug.
- `.lamina/business-context.md` and `.lamina/personas.json` are evidence inputs. They are useful, editable files, but not shared canonical graph state.
- Legacy run files are untouched, excluded from observation, and have no runtime authority.

Git identifies branches and source revisions. A `GraphVersion` records graph membership and validation at a particular source revision. A human-readable implementation plan, report, or fix list is a projection from that version—not a second source of truth.
